01

The Problem Before CI/CD

Integration hell, codebase freezes, and releases twice a year — the world CI/CD was invented to escape.

PICTURE THIS
Five developers each work alone on their own feature branch for three weeks, never merging into the main codebase. On release day, everyone merges at once. Every merge conflicts with every other merge. Nobody remembers why they wrote half of this code three weeks ago. This multi-day nightmare of untangling conflicting changes has an actual name in the industry: integration hell.
3 weeks of silent, isolated work → one catastrophic merge → a frozen codebase while everyone untangles it

Three symptoms of a pre-CI/CD world

  • Integration hell — When multiple branch merged & we get merge conflict. Merging weeks of divergent code at once means dozens of conflicts discovered simultaneously, with no clear owner for any single one
  • Codebase freeze — nobody can merge new work while the team is busy untangling the last release, so progress on everything else stalls
  • Infrequent releases — because releasing is painful and risky, teams ship every few months instead of every day, so every release bundles a huge, riskier batch of changes
WHY THIS MATTERS TO YOU

Every CI/CD tool, every automated test, every deployment strategy in the rest of this note exists to solve exactly the picture above. If you understand why integration hell happens, every tool that follows will make sense as "the fix for that specific pain," not as an abstract best practice.

02

CI/CD Fundamentals

Continuous Integration concepts, how deployment workflows are structured, and the tools that run them.

CI vs CD — two different promises

Continuous Integration (CI): every developer merges their code into the shared main branch frequently (multiple times a day), and each merge is automatically built and tested. Small changes, integrated constantly — the direct opposite of the 3-week isolated branch from Module 1.

Continuous Delivery / Deployment (CD): once code passes CI, it's automatically prepared for release (Delivery) or automatically pushed live (Deployment) — no manual "let's schedule a release meeting."

the standard CI/CD flow — every box runs automatically, no human clicks "deploy"

Analyzing a deployment workflow — what to actually look at

When you open somebody's pipeline config for the first time (a .yml file, a Jenkinsfile, whatever), don't read it top to bottom like prose. Ask three questions:

  • What triggers it? — a push to main, a pull request, a nightly schedule, a tag?
  • What stages run, in what order? — this is the pipeline flow above; find where build ends and test begins
  • What gates the next stage? — does a failed test actually stop deployment, or just send a warning?

Tools used in CI

GitHub Actions — lives in your repo, easiest to start with GitLab CI/CD — built into GitLab, all-in-one platform Jenkins — self-hosted, maximum customization, steeper setup CircleCI — cloud-native, fast builds, strong caching Azure DevOps — best fit inside the Microsoft ecosystem

Across current industry surveys, GitHub Actions, Jenkins, and GitLab CI consistently top the adoption charts (source) — which one to learn first usually comes down to where your code already lives.

TRY THIS — IN CLASS
Open any public GitHub repo's .github/workflows/ folder. Find the trigger (top of the file, usually on:), then count the stages. You don't need to understand the syntax yet — just map it to the Commit → Build → Test → Deploy diagram above.

Automated Testing Pipeline

Automatic test execution — the gatekeeper that decides whether code is even allowed to reach deployment.

ANALOGY
Think of an airport security checkpoint. Nobody manually re-checks every passenger by hand each time — there's an automated scanner every single person walks through, no exceptions, no "just this once." A test pipeline is that scanner for code: it runs the exact same checks on every single commit, tirelessly, before anything is allowed through to the gate.
the testing pyramid — lots of cheap fast tests at the base, fewer expensive slow ones at the top

What "validate before deployment" actually means

Every commit triggers this sequence automatically, with zero human involvement unless something fails:

  • Unit tests run first — fastest, cheapest, catch the most obvious breakage in seconds
  • Integration tests run next — check that different pieces (API + database, frontend + backend) actually work together
  • End-to-end tests run last — simulate a real user clicking through the app, slowest and most expensive, so there are fewer of them
  • Any failure blocks the pipeline — deployment simply does not happen until every gate passes green

✅ Tests pass

Pipeline proceeds automatically to packaging and deployment. No human needs to say "looks good to me" — the green checkmark is the approval.

❌ Tests fail

Pipeline halts immediately. The developer who pushed the breaking change gets notified directly — often before their coffee is done.

REAL USE CASE

This is exactly what stops a broken login page from ever reaching real users. Without an automated gate, that bug is only caught when a human happens to test it manually — which, on a Friday afternoon before a long weekend, is precisely when it doesn't happen.

COMMON MISTAKE
Writing only end-to-end tests because "they test the whole real app." E2E tests are slow and expensive to maintain — a healthy pipeline has far more unit tests than E2E tests, not the other way around.
TRY THIS — IN CLASS
For any small feature (like a login form), call out loud: one thing you'd unit test, one thing you'd integration test, and one thing you'd only catch with an end-to-end test. Notice how the scope gets bigger and the test count should get smaller at each level.

CD / Deployment Strategies

Blue-green, canary, and rolling deployment — three different answers to "how do we release without downtime or disaster."

Blue-Green Deployment

Two identical environments exist side by side. Only one serves real traffic at a time; the other sits idle, ready to receive the new version.

blue-green — instant switch, instant rollback (just switch back), but you pay for two full environments

Canary Deployment

Named after the "canary in a coal mine" — send the new version to a small slice of real users first. If it survives, gradually increase the slice. If it doesn't, only a few users ever saw the problem.

canary — traffic to the new version grows in stages, each one monitored before advancing to the next

Rolling Deployment

Instead of two full environments, existing server instances are replaced one at a time (or in small batches) with the new version — no idle duplicate infrastructure needed.

rolling — no duplicate infrastructure, but a rollback means rolling the same process backward, instance by instance

Which one, when?

Blue-Green

Best when you need instant, guaranteed rollback and can afford double infrastructure cost.

Canary

Best when you want real user feedback on a risky change before it reaches everyone.

Rolling

Best default for routine updates when you don't want to pay for duplicate environments.

Tools used in CD

Argo CD — GitOps-native, Kubernetes deployments Spinnaker — supports blue-green & canary out of the box AWS CodeDeploy — managed blue-green/rolling on AWS Harness — enterprise CD with progressive delivery GitLab CI/CD, Jenkins — can drive any of the above with the right config

Pipeline Debugging

CI/CD troubleshooting — what to actually check when the pipeline turns red at 6pm before a demo.

the first branch that matters isn't "what's broken" — it's "which stage failed"

The debugging order that actually saves time

  • Find the failed stage first — build, test, or deploy. This alone eliminates most of the wrong guesses.
  • Read the actual log output, not just the red X — the real error is almost always in the last 10-20 lines of that stage's log
  • Ask "did this work locally?" — if yes, suspect environment differences (missing env variable, different dependency version, different OS)
  • Check what changed since the last green run — the most recent commit is the most likely suspect, every time
  • Re-run before assuming it's your code — a flaky test or a temporary network blip can fail a pipeline with nothing wrong in the code at all

🔴 Build stage failed

Usually: a missing dependency, a typo the compiler catches, or a version mismatch between your machine and the pipeline's environment.

🟠 Test stage failed

Usually: an actual regression — or a "flaky" test that fails intermittently due to timing/network, not your logic.

COMMON MISTAKE
Immediately re-running the pipeline hoping it "just fixes itself" without reading the log first. Sometimes that's right (a flaky test), but doing it as a reflex means you'll eventually ship a real bug that happened to pass on retry.
REAL USE CASE

A pipeline that was green yesterday turns red today with zero code changes — nine times out of ten, that's an external dependency (an API the tests call, a package registry, a service being down), not your codebase. "Which stage, what changed" still applies — you're just checking outside the repo instead of inside it.

TRY THIS — IN CLASS
Look at a real failed pipeline run (yours, a classmate's, or any public repo's Actions tab with a red X). Before reading a single line of the error, first identify only which stage failed. Then read the log. Notice how much that first step narrows down where to look.
